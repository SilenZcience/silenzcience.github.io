The cat_win project, for me, is the perfect excuse to learn something new. It is a project that I am using to explore new ideas, techniques and concepts while also creating a tool that is actually useful in various ways. It began as a simple cat clone for Windows (Powershell used to not have a native cat command) and over time grew into an overengineered text-processing and analytics toolset for the command line. It ships as two executables, catw as the classic cmd-utility and cats for working interactively inside a REPL. The development of cat_win stretches over many years and 1,700 commits.

Observation 001 - Origin

Everyone needs an origin story.

The original idea behind this project was rather simple: read files, print them to standard output, and do it on a system nobody ever wrote a native cat for. It seemed like a small, trivial project maybe, but it set a milestone in learning to program in the first place. The original version was developed and published back in 2022 at Cat_For_Windows but existed as a local project I had been using long before that.

The command that can read a file should also be able to manipulate and transform it, and maybe even provide information about it. One feature lead to the next, and the project grew into an overengineered jumbled mess that long left the territory of clones and simple utilities. After multiple large refactors and partial rewrites the code base however is rather clean now in comparison to the previous versions. Today it is a toolkit for file inspection, text transformation, searching, filtering and encoding, as well as analysis and text processing, all in one place. It even contains a decent editor, hexeditor and my very own diffviewer.

Observation 002 - The Tool

Content, components and capabilities.

On a broad scale, cat_win provides a wide range of functionalities. It accepts files, standard input and URLs. Every line of output can be prefixed or suffixed with information like line numbering or line length. The output can be sorted or formatted, filtered and transformed. Some of these arguments accept Python-style slices like [6:] and [::-1], so text can be cut and reversed line by line. Queries find literals or patterns (regex), while leaning into the functionality of the 'grep' tool. Summaries can be generated to provide information about wordcount, charcount or a simple overview of files and directories. Text can be explored in a pager style similar to the 'more' or 'less' tool. The own implementation of viewing attributes can be compared to 'libmagic' or the 'file' utility. Viewing the input in different interpretations is of course possible, as the tool supports a bin-/ and hexviewer as well as base64. Next to these cat_win includes many more features in an ever expanding landscape of utility. For in-depth technical documentation, refer to the DOCUMENTATION.md file.

The interactive sibling, cats, opens the same feature set as a live session inside a simple REPL. Instead of restarting the program for every input, it allows adjusting parameters on the fly. Especially useful for experimentation and quick calculations. The built-in desk calculator and number conversion to different numerical bases are one of many features predestined to be used inside the interactive environment of cat_win.

Observation 003 - Curses Applications

An editor no one uses.

The text editor, opened with -!, --edit, is a full terminal application built on the curses library which loads files lazily, so large input opens quickly. Movement is implemented at every scale: character by character, word by word, page by page, and even supports using the mouse instead of keyboard.

Ordinary editing is only the beginning. There is syntax highlighting for many languages, with a manager to pick your own scheme. Find and replace works with literals or regular expressions. Undo and redo carry the full history of changes, and a context menu gathers the frequent actions. The editor can open a file manager to switch files quickly, and even supports loading a file's git history.

Everything you would expect from a simply basic text editor is present and functional. Additionally there are features that nobody strictly needs. That's me having fun and implementing things I find interesting to play with. The classic Unix 'fg' command to bring a background process to the foreground is simulated by allowing to save the entire viewstate of any curses application to disk and restore it even after restart.


A hexeditor no one wants.

The hex editor, opened with -#, --hexedit, fundamentally works identical to the text editor. The file again loads lazily. You navigate the content byte for byte and type new values directly over the current one, insert new bytes to the left or right of the cursor, and delete whole chunks with a single key. Search accepts byte sequences, or switches to plain-text search when a human phrase is easier to remember.

The hexeditor has access to the same file manager to allow for easy navigation between files and git histories. Again mouse support is fully integrated as well. There are of course far better alternatives out there to use, but this one belongs to me and it gets the job done most of the time. It is not intended to become a fully fleshed out project by itself but rather a basic tool for the most common use cases.


A diff viewer no one asked for.

The diff viewer, opened with -?, --diff, shows two files side by side and walks through their differences. Given a single file, it compares against the git history instead, which is a helpful mode for tracking changes over time. In combination with another command argument it is even possible to watch the same file for modifications over time while keeping the diff viewer open. In this case the tool will periodically scan for file changes and update the view accordingly.

The diff viewer allows to tune the similarity ratio manually at which lines are paired together. This simple feature is the main reason for implementing an own diff viewer in the first place as it is a functionality I miss in the most common diff tools. Oftentimes some differences intuitively belong together but are still not accepted by the default algorithms because they barely miss the similarity threshold. In cat_win you can simply adjust this threshold such that more complicated changes are easier to track.

Observation 004 - Customization

Configuration instead of compromise.

Nothing about cat_win has to stay the way I shipped it. The --config parameter opens a menu of the default settings the tool starts with, and --cconfig does the same for the color scheme. Every color that cat_win displays can be customized and there exists a vast amount of options to tailor the behaviour of any program component. From default file encoding to auto indentation inside the editor everything is customizable.

These configuration files live in the platform-standard config homes: AppData, XDG_CONFIG_HOME or Application Support. Using the installation path is not viable since the python package would fragment on uninstall using pip and this way the configuration survives an update. Flags exist to reset the whole configuration to defaults or remove the files completely, since it is massively annoying when programs leave behind traces on uninstallation.

Observation 006 - Philosophy

Lightweight and compatible.

The design goals of cat_win are simple: lightweight by using minimal dependencies and maximal compatibility to allow cross-platform use. The runtime requirement reaches back to Python and PyPy 3.6, old enough that the tool has to work hard to stay polite with it, and standalone executables for Windows, Linux and macOS are built with PyInstaller. You can use it on a machine that do not have any Python version installed.

The engine under all of it is deliberately small. The clipboard support is an optional extra, and the color patch for legacy Windows terminals is optional too. Everything else ships with the standard library. Sadly the curses library does not exist natively on Windows which is why the tool does depend on the windows-curses package when opening any of the curses applications on that platform. The rest of the tool does however keep working even when these dependencies are not available.

Keeping dependencies this small is more than a compatibility necessity. It is also an opportunity to learn about technologies from scratch, and to have fun implementing them from the ground up.
It is honest to say the project is a little overengineered at this point. Not everything strictly needs to exist or makes sense in the context of the project. But that has always been part of the point. Since it is primarily a toolkit from me for me, it is simply pragmatic to have all the features I need in one place. It also means that whenever a feature feels awkward, I am the first user to notice, because I am the user of every release. And being the owner of the tool I get to instantly adjust any annoyances I encounter.


AI notice.

The cat_win project is, and will always remain, one hundred percent human written. cat_win dates back to an era before AI and like all of my projects from that time, and I do not intend to ever let an AI touch it. Handing it over would, in my eyes, ruin the idea behind a learning project. It would also taint the giant body of work I have built myself over the years. Every single line of code has been manually typed and reasoned about. The documentation and the changelog are no exception: entirely structured, designed and written by me. When future me reads this code, I want to know exactly who to blame for this shitpile.
